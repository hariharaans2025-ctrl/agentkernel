# Model-generated packed atomic pair experiment

Both model-generated atomic implementations passed the protected correctness workload and measured faster than the mutex baseline in this Sandbox microbenchmark. Atomic store/load is the preferable candidate for this replacement-only API because it does not consume the previous value; exchange is retained as the requested comparison.

| Median of 10 batch averages | Mutex | Atomic exchange + load | Atomic store + load |
|---|---:|---:|---:|
| Single-thread mixed read/write (ns/op) | 6.55 | 1.23 | 1.23 |
| Concurrent writer loop (ns/write) | 35.50 | 5.63 | 3.40 |
| Concurrent reader loop (ns/read) | 36.21 | 4.08 | 3.52 |
| Concurrent wall time / all operations (ns/op) | 18.63 | 2.91 | 1.84 |

The concurrent wall-time row is inverse aggregate throughput, not individual-operation latency. Per-thread rows are average loop time per operation, including loop/validation overhead, then summarized by the median across runs. No p95/p99 latency or wait-free guarantee was measured.

## Correctness and origin

- Mutex baseline: assistant-authored, verified once in the original experiment; its unchanged verification evidence is referenced here.
- Exchange and store variants: generated by Qwen/Qwen3-30B-A3B-Instruct-2507, corrected by that model after linker feedback, and compiled without manual changes to its C code.
- Each variant passed compilation, protected original tests, 100/100 stress executions, the semantic oracle, and 3/3 required TSan runs.
- The protected harness checked arbitrary signed 32-bit pairs, including extreme values, concurrent pair consistency, and the final writer values. Runtime atomic_is_lock_free returned true for the actual uint64_t atomic object in both atomic modes.
- Both fields are packed into a single 64-bit atomic object. Each reader takes one acquire load and decodes both fields from that one snapshot. The exchange publisher uses acquire-release exchange; the store publisher uses release store.
- The original pair_snapshot fixture exposes two ordinary integers directly. This experiment introduces a set_pair/get_pair abstraction and changes representation; it is not a drop-in patch preserving that old interface. No frozen fixture, benchmark score, prompt, or earlier evidence was modified.

## Timing method and limits

The same protected harness was used for all variants. Correctness runs used GCC -O1 with scheduling yields in the harness; TSan used Clang. Performance binaries used GCC -O3 without TSan. Every variant received one discarded warmup, then 10 timed samples in rotating variant order. Each timed phase performs 500,000 writes and 500,000 reads; scheduling yields are disabled equally for all variants in the timed phase.

Timing was taken inside the Sandbox using CLOCK_MONOTONIC, with reported resolution of 1 ns. API latency, remote uploads, compilation, and model inference are not included in the ns/op measurements. The observed environment identified x86_64, AMD EPYC 9654, four virtual CPUs, and KVM. CPU affinity, placement, frequency, and host contention were not controlled. Writer and reader use fixed iteration counts and may finish at different times; this does not guarantee sustained contention for the whole interval. Small hot-state workloads do not represent large real repositories or end-to-end application latency.

| Per-thread average range across 10 samples | Mutex | Exchange | Store |
|---|---:|---:|---:|
| Writer ns/op | 24.33–66.56 | 5.32–5.90 | 3.11–4.61 |
| Reader ns/op | 28.54–67.28 | 3.92–4.66 | 3.21–5.30 |

## Preserved failed attempt and cost

The first model response omitted get_pair in both variants. A runner AttributeError also stopped the original experiment after mutex verification; its evidence remains unchanged. The continuation used exit_code/timed_out checks, recorded actual linker errors for both original model variants, and made exactly one correction call. It reused the completed mutex verification and freshly verified both corrected atomic variants. No generation was silently replayed.

Total model usage: **2 calls, 1,876 tokens, $0.0002904 calculated inference cost**. The two pre-run call reservations total $0.0548864, below the revised $0.06 bound and within the $10 pilot. Sandbox access is free per user confirmation. No training was run.

## Application decision

Prefer store/load for this particular API if the measured advantage reproduces in a representative deployment workload. Use exchange when the previous value is actually needed, or compare-exchange for conditional updates. Larger state that does not fit into one supported atomic object needs a different design; two separate atomic fields do not preserve a paired snapshot. This optimization targets application data access, not model-token generation, HTTP requests, or the duration of the full verification campaign.

GCC documents the distinct load/store/exchange operations and lock-free queries: [GCC atomic builtins](https://gcc.gnu.org/onlinedocs/gcc/_005f_005fatomic-Builtins.html).
